# IVY Bulk Upload — Business Rules

**Every rule the application applies to your data after you press Browse, written in plain English.**

SCDO / Synthetic CDO Processing · Screen: `BulkUploadByIvy` · Branch `newlogicfordeutchebank` · Working tree as at 28 Aug 2026

---

## How to read this

This document explains the **rules** — what the application actually does to each value it reads out of your trustee report and data files.

Rules are grouped by the schema they act on, not by where they sit in the code, because the same schema is touched by several routines at different points in the run. Each rule is written as a plain statement of the form *"if this, then that"*.

For the same material organised **by column** — one entry for each of the 347 columns across the twelve schemas, including the columns that carry no rule at all — see [ivy-bulk-upload-column-rules.md](ivy-bulk-upload-column-rules.md).

Example, taken from the Test Results section below:

> **If every row's `is_tr_test` is blank, set them all to `N`.**
> The trustee report does not always mark which tests are trustee tests. If the column came back completely empty for the deal, the application assumes none of them are and stamps `N` on every row. If *some* rows have a value and others don't, only the blank ones are set to `N`. If the column was never mapped at all, an advisory is raised — *"is_tr_test not mapped in xml, do u want to continue?"* — and processing carries on.

Where a rule exists only for one trustee or one deal, that is stated. Where a rule fires an error, the exact message is quoted so it can be matched against what appears in the error report.

**A note on order.** Rules do not all run at once. Section 16 gives the execution order, which matters: a value can be set by one rule and then overwritten by a later one.

## 1. Value cleaning — applies to every field

These run on **every value from every schema** before it is stored. They are the first thing that happens to a number or a date pulled out of the report.

### 1.1 Dates

Applies to every field configured as a date (maturity, defaulted date, trade date, settlement date, paydown date, and every column the database declares as a datetime).

- **`dd-MMM-yyyy` is rewritten to `MM/dd/yyyy`.** So `15-Jan-2026` becomes `01/15/2026`.
- **A date carrying a time is stripped of the time.** `01/15/2026 12:00:00 AM` becomes `01/15/2026`.
- **Any date outside the years 2000–2099 is blanked.** A year of 1900 or 2100 is treated as "no date", not as a real date.
- **If the value cannot be read as a date at all**, the field is left blank and an error is raised: *"Problem Converting Maturity/Defaulted/Trade/Settelement/Paydown Date"*.

### 1.2 Ambiguous day/month order

Before anything else, the application checks whether the report is using **DD/MM** rather than the expected **MM/DD**. It samples trade date, settlement date and maturity. If it concludes the file is DD/MM, **every date column in every tab** is converted to MM/DD/YYYY.

If the same column carries more than one format, the deal fails: *"Multiple Date format present in the deal in table number …"*.

### 1.3 Numbers

Applies to roughly 80 fields registered as numeric (balances, rates, spreads, prices, percentages).

- Thousands separators are removed: `1,234.56` → `1234.56`
- Percent signs are removed: `4.25%` → `4.25`
- **Brackets mean negative**: `(1234.56)` → `-1234.56`
- Comparison signs are stripped: `>`, `<`, `=`
- Asterisks are stripped; if an asterisk survives, the value is blanked entirely
- A lone `-` or a lone `.` becomes **null**, not zero
- A value containing `^` (used by the extraction engine to pack multiple readings into one cell) has trailing letters removed and is reduced to digits and the decimal point. A leading minus is preserved. **Exceptions:** `sp_recovery_rate` is left alone because `^` is meaningful there, as is `test_trigger` when it contains a `/` (a min/max trigger).

### 1.4 Percent and slash stripping

- The `%` sign is removed from **every field except** issuer name, industry name, S&P industry, test name, misc name and account name — the fields where a `%` could legitimately be part of a name.
- Forward slashes are stripped from every field except those same name fields plus maturity, trade date and settlement date.

### 1.5 Dash and N/A handling

For every field except `result` and every table except Test Result:

- **A lone `-` becomes blank** — unless the field name contains `watchlist`, `outlook` or `_wo`, where a dash is a real value.
- `N/A` and `N/A%` are left as-is at this stage; later rules blank them per schema.

### 1.6 Value standardisation from lookup

- Any value that appears in the **PDF data lookup** for that column is replaced by its standardised equivalent. This is how "Aaa " and "AAA" from different trustees end up as one value.
- Any text fragment listed in the **replace-value lookup** is substituted wherever it appears in any value.

### 1.7 Length and type checks

- **If the captured text is longer than the database column allows**, the deal fails with *"Its length is greater than actual length"*. In practice this almost always means the extraction picked up two columns as one.
- **If the value cannot be converted to the column's data type** (text in a numeric column, for example), the deal fails with *"Validation fail it should be \<type\>"*. Certain columns are exempted via a "datatype checking not required" list.

### 1.8 Permitted-value validation

Around 45 fields are validated against a permitted-value list: all rating fields (Moody's, S&P, Fitch, DBRS Morningstar, KBRA, country, issuer, and the CCC / Caa concentration-limit variants), all watchlist and outlook flags, all currency fields, payment frequency, coupon type, coupon calendar method, index type, security ID type and misc type.

- **If the value is not on the list, the deal fails** with *"Validation Fail"* naming the column and the value.
- For fields on a separate "column value validation" list, a value not on the list is **recorded for review** rather than failing — it appears in the mismatch grid.

### 1.9 Yes/No normalisation (data files only)

For any field whose permitted values include `Y` and `N`:

- **`1` becomes `Y`**, **`0` becomes `N`**.
- **Except** `loan_lien` and `default_status`, where 1 and 0 are real values.
- After conversion, if the value is still not on the permitted list, the deal fails with that column's own configured error message.

### 1.10 Numeric range ceiling

**Six rate fields must not exceed 20**: current interest rate, spread, adjusted spread, PIK coupon, index cap, index floor.

A value above 20 fails the deal: *"Validation Fails For Column \<x\> And Value \<y\> It should not be greater than 20"*. This is a sanity ceiling — a spread of 450 means basis points were captured where a percentage was expected.

### 1.10A The blank-cell fill *(reworked, uncommitted)*

Where a collateral cell is still empty after the load, a second reading of the report can fill it. **A value written by this path is not a raw value** — it runs the whole cleaning chain inline before it is stored, in this order:

1. Trim; discard if empty.
2. Lone `-` → blank, **except** for `result`, for `N/A`, and for any column whose name contains `WATCHLIST`, `OUTLOOK` or `_WO`.
3. **S&P recovery rating reduced to its first digit** — this is where that rule actually lives.
4. Date columns rewritten to `MM/DD/YYYY`, time stripped, year window enforced; an unreadable date raises *"Problem Converting Maturity/Defaulted/Trade/Settelement/Paydown Date"*.
5. Numeric columns stripped of separators, percent signs, brackets, comparison signs and asterisks, with the caret rule and its `sp_recovery_rate` exemption applied.
6. PDF data lookup substitution.
7. Bracketed-number strip on industry names.

**Only then is the cell written.** A blank that survives all seven steps stays blank.

### 1.11 Identifier whitespace *(new, uncommitted)*

Before anything else is done with the parsed data, **every space is removed from `cusip`, `isin`, `loanx_id`, `lin` and `multiple_id`** — leading, trailing and in the middle — along with non-breaking spaces, zero-width characters and byte-order marks. `BL 123 456 7` becomes `BL1234567`. The count of values cleaned is written to the run log.

## 1A. Rollup — how report rows become collateral rows

Before any of the rules below apply, the extracted report has to be turned into rows. A trustee report rarely presents one asset as one tidy line: the same asset's ratings, balances and identifiers can be spread across several physical lines, and different columns can start at different lines. The rollup is what reassembles them, and it explains most "why did this end up on the wrong row" questions.

### 1A.1 The anchor

Every rollup is keyed on one column, **`ColumnValueToUpdateBy`** — in practice the issuer name or the identifier the mapping team nominated. That column defines how many real rows there are. Everything else is fitted around it.

**A blank anchor ends the table.** Rows below the first blank anchor value are not read. (For the Tranche Description table the test is different — reading stops only when the first seven columns are *all* blank.)

### 1A.2 Column packing

Each column is first compacted independently: **within a column, only the first occurrence of each distinct value is kept, and the survivors are packed upward**, leaving blanks at the bottom. A value repeated down a column collapses to one entry. Two columns are exempt and keep every value in the order reported — the anchor column itself, and the deal's configured default column.

### 1A.3 Matching

For each column, values are matched against the anchor and written into the matching row. Three things govern this:

- **Matching is exact, but only after normalisation.** Both sides have `€ Â * \ / & ) ( ^ % $ # @ ! ~ ' : " ; , . | { } [ ] + - _ \`` replaced by spaces, then **all spaces removed**, then uppercased. So `S.à r.l.` and `S a r l` are the same value. This is why punctuation differences between sections do not break the rollup.
- **Longest first.** Within a column, candidate values are tried in descending order of length, so the most specific value claims its row before a shorter one can.
- **A value is written only into a blank cell.** If the target cell already holds a *different* value, the incoming value is not overwritten — it is set aside.

### 1A.4 What happens to values that don't fit

This is the part worth understanding, because it is visible in the output. A value that matched nothing, or that collided with a value already in place, is handled in this order:

1. **It is dropped into the first blank cell in its own column, below the matched block.**
2. **If there is no blank cell, a brand-new row is created holding just that one value.**

**That is where single-column "orphan" rows in the ASCII come from** — a row with an issuer name and nothing else, or a rating and nothing else. It is not a bug in the extraction; it is the rollup refusing to discard a value it could not place.

Three columns are excluded from matching entirely: `ColumnValueToUpdateBy`, `DISPLAY_SEQ_COLL` and `Recovery_Classes`. The Tranche Description table is not column-matched at all — its first seven columns are copied straight through.

> **A note on the "contains" match.** The rollup used to fall back to a substring match when the exact match failed — so `ABC Holdings` would match a row anchored on `ABC Holdings Ltd`. **That fallback is switched off**, under "Roll-Up and Insert Assets Logic". Matching is now exact-after-normalisation only, which is stricter and produces more orphan rows than it used to, but no wrong-row placements.

### 1A.5 Amounts apportioned on rollup

Where several report rows roll into one collateral row **and** the summed principal balance of the source rows equals the consolidated balance (within 0.1), four amounts are **apportioned pro-rata by each row's share of principal balance**, but only where the target is currently empty:

**`par`, `haircut_amt`, `capitalized_int`, `recovered_amt`**

This is the only place those four are derived rather than read. If a rolled-up asset's par looks like an odd fraction rather than a reported figure, this is why.

## 1B. How a data file row is matched to a collateral row

The Moody's data files do not carry the collateral row number, so each file row has to be matched back to an asset. The application tries identifiers **in this fixed order, first hit wins**:

1. `TRUSTEE_ID`
2. `loan_identifier`
3. `isin`
4. `cusip`
5. `reference_cusip`
6. `loanx_id`
7. **`facility_id`**
8. `issuer_name`

An identifier is only tried if the collateral row has a value for it **and** that column was mapped in the data file. If a lookup returns no row, the next identifier is tried. **Issuer name is the last resort**, and where it is used the match falls back to the row sequence and the rollup lookup.

Two points that catch people out:

- **`facility_id` is a real match key**, matched together with security type. On deals where the trustee report and the Moody's file share nothing but the facility ID, this is the only thing joining them.
- **Where the deal uses the multiple-issuer-name feature, the identifier chain is skipped entirely** and the multiple-issuer sequence number is used instead.

**A blank principal balance is set to `0.00` before matching**, so a zero-balance asset still participates.

## 2. Identifier classification

The trustee report often puts every identifier in one column. These rules work out what each value actually is and move it to the right field. They run in the order below, first match wins.

### 2.1 The core classification rules

Applied to any value found in `multiple_id`, `optional_id`, `security_id_1`, `trustee_id`, `cusip`, `isin` or `loanx_id`:

| The value is | …and | Then it is treated as |
|---|---|---|
| 9 characters, no underscore, alphanumeric only, contains a digit | it starts with `BL` | **Trustee ID** — `BL` prefixes are trustee-internal, not CUSIPs |
| 9 characters, no underscore, alphanumeric only, contains a digit | it does not start with `BL` | **CUSIP** |
| 12 characters, no underscore, alphanumeric only, contains a digit | it passes the ISIN check-digit test | **ISIN** |
| 12 characters, no underscore, alphanumeric only, contains a digit | it fails the check digit, but passes after replacing the letter `O` with zero | **ISIN**, with the O→0 correction applied |
| 12 characters | it fails the check digit either way | **Trustee ID** |
| 8 characters, no underscore, starts with `LX`, alphanumeric, contains a digit | | **LoanX ID** |
| anything else | | **Trustee ID** |

**The check-digit test** is the standard ISIN Luhn validation: the first two characters must be letters (the country code), the last must be a digit, and the whole thing must satisfy the modulus-10 checksum.

### 2.2 Don't overwrite what's already there

If the target field already exists as its own column in the source data, the value is **left where it is** rather than moved. The application will not overwrite a real CUSIP column with something it guessed was a CUSIP.

### 2.3 The same identifier in two places

- **If Trustee ID equals the LoanX ID, ISIN, CUSIP or Bloomberg ticker on the same row, the Trustee ID is cleared.** Holding the same value twice adds nothing.
- Same rule is applied to Principal Activity rows.
- When LoanX ID is reclassified as an ISIN or CUSIP: if that target field is already populated with the same value, LoanX ID is simply cleared. If the target is empty, the value moves across. If the target is populated with something *different*, the value moves to Trustee ID instead.

### 2.3A Promotion back out of Trustee ID

Trustee ID is the catch-all, so it accumulates values that were never really trustee identifiers. **A later pass re-reads it and promotes what it can**, clearing the Trustee ID each time:

- **9 characters, alphanumeric, no underscore, containing a digit, not starting `BL` → moved to CUSIP.**
- **12 characters passing the ISIN check digit** — retried once with letter `O` replaced by zero — **→ moved to ISIN.**

This runs after the initial classification, which is why a value can appear in Trustee ID at one stage of the run and in CUSIP at the next.

### 2.4 Bloomberg tickers

**Any identifier starting with `BBG` is a Bloomberg ticker.** If found in ISIN, LoanX ID, CUSIP, reference CUSIP, loan identifier or Trustee ID, it is moved to `bloomberg_ticker` (provided that field is empty) and cleared from where it was found.

### 2.5 Junk characters in Multiple ID

**Full stops and asterisks are stripped from Multiple ID** — unless the issuer name contains "PAR", where they may be meaningful.

### 2.6 Bonds have no LoanX ID

**If security type is `Bond`, LoanX ID is cleared.** A bond does not have a loan identifier.

### 2.7 Trustee ID punctuation for non-PIK assets *(collateral only)*

For any asset whose issuer name does **not** end in " PIK", punctuation in the Trustee ID is stripped down to letters, digits and underscores. PIK assets keep their `*` and other markers, which carry meaning.

### 2.8 Generated identifiers

If a collateral row has no security ID at all, one is generated as `{deal id}{year}{month}{4-digit sequence}` and the type is set to `DAT`. Duplicate security IDs within a deal are cleared first, so the same generated ID is never issued twice. Transaction rows follow the same rule, continuing the sequence from where collateral left off.

- Security ID type defaults to `LIN` when blank.
- Security ID type is set to `DAT` when the security ID starts with the deal ID.

### 2.9 LoanX ID format validation

A separate check validates that LoanX IDs are in a valid format. Failures raise *"updated not done for LoanXID for collateral"*.

## 3. Currency

### 3.1 Splitting the currency out of the amount

Trustee reports frequently write `USD 1,234,567.89` in a single cell. The application splits every such value: **digits, commas, full stops, and the minus sign stay with the amount; everything else becomes the currency code.**

This is applied to:

| Schema | Amount field | Currency field |
|---|---|---|
| Collateral | `principal_balance` | `currency_code` |
| Collateral | `mv_market_value_par` | `mv_market_value_currency` |
| Collateral | `principal_balance_in_original_currency` | `original_currency` |
| Account Balance | `account_principal_balance` | `account_principal_currency` |
| Account Balance | `account_interest_balance` | `account_interest_currency` |
| Account Balance | `account_apex`, `account_revolver`, `account_delayed_funding` | matching `_currency` fields |
| Account Balance | `account_revolving_reserve`, `account_synthetic_collateral`, `account_liquidity_reserve`, `account_interest_reserve`, `account_expense_reimbursement`, `account_supplemental_reserve` | matching `_currency` fields |
| Account Balance | `total_collateral_balance` | `total_collateral_balance_currency` |
| Misc Account | `account_balance_orig`, `account_balance_global` | `account_currency` |
| Miscellaneous | `misc_amt` | `misc_currency` |

**The extracted currency code must be valid.** It is first checked against the PDF data lookup for a standardised equivalent; failing that, against the permitted currency list. **If it is on neither, the deal fails**, naming the field: *"account_principal_currency Is Wrong, The Value Is :: …"*.

### 3.2 Filling in a missing currency

**If the deal uses exactly one currency across all collateral**, that currency is copied into every blank currency field in Principal Activity, Transactions, Misc Account, Miscellaneous and Account Balance. If the deal is multi-currency, nothing is filled in — the application will not guess.

### 3.3 Currency is mandatory

**If no collateral row carries a currency code at all, the deal fails**: *"Currency Code is blank for this deal. Please map currency code and reupload."*

### 3.4 Misc Account currency from the account name

Where the account name itself carries a currency — `EUR Principal Account`, `Interest Account USD` — that currency is written into `account_currency` and the global balance is cleared, so the balance is not double-counted across currencies.

- **`Euro` at the start of a name is read as `EUR`**; `EURO` at the end likewise.
- The deal's own base currency is excluded from this matching, so a USD deal's "USD Principal Account" is not re-flagged.
- Skipped entirely if the report supplied `account_currency` directly.

## 4. Collateral

### 4.1 Payment frequency

Read from free text and normalised:

| Report says | Stored as |
|---|---|
| starts `1` … `mo` | monthly |
| starts `2` … `mo` | bi-monthly |
| starts `3` … `mo` | quarterly |
| starts `6` … `mo` | semi-annually |
| starts `12` … `mo` | annually |

**From the index name:** if `idx` mentions 1 week (`1w`, `1 week`, `LIBOR (1 week)`) and payment frequency is blank, it is set to **Weekly**. Two weeks likewise gives **Bi-Weekly**.

### 4.2 Coupon calendar method

Anything matching `a…/360` is normalised to **`act/360`**.

### 4.3 Index (IDX)

Three rules, in order:

1. **If no asset has an index and the deal is single-currency**, the index is derived from the currency: `USD` → **LIBOR**, `EUR` → **EURIBOR**, `GBP` → **GBP LIBOR**. Only applied to rows that have a payment frequency.
2. **If no asset has an index**, it is derived from the payment frequency for every non-fixed-coupon asset: Monthly / Weekly / Bi-Weekly → `LIBOR1`, Bi-Monthly → `LIBOR2`, Quarterly → `LIBOR3`, 4 Months → `LIBOR4`, and so on through to Annually → `LIBOR12`.
3. Two stored procedures then apply the deal's configured index and payment-frequency mapping, including a separate SOFR variant.

### 4.4 Equity assets

Equity is the most heavily special-cased security type.

- **A maturity of 1900 or 2100 on an equity asset is cleared.** These are placeholder dates, not real maturities.
- **An equity asset with no maturity is given the trustee run date plus two years.** Applied twice in the run, before and after the data-file load.
- **Equity assets have coupon type, index, current interest rate, spread, adjusted spread and index floor all cleared.** Equity does not pay a coupon.
- **Equity assets have default status cleared.**
- **If an equity asset's principal balance is zero but it has a par value, the par is copied into principal balance.** Recognised equity security types for this rule: `Equity`, `Equity Security`, `Equity securities`, `Specified Equity`, `Warrants`, `Warrant`, `Common stock`, `Preference Equity`, `CS`, `EQ`, `EQ1`, `FU`, `PE`.
- **If a secondary collateral section reports an equity position for an issuer whose primary balance is zero, the secondary balance is used.** Issuers that appear only in the secondary section are added as new rows.

### 4.5 Fixed-coupon assets

**Assets with coupon type `FIXED` have index, spread and adjusted spread cleared**, and index adjustment cleared. A fixed asset has no floating-rate components.

### 4.6 Negative values corrected to zero

The following are floored at zero: `recovered_amt`, `current_interest_rate`, `spread`, `spread_adjusted`, `index_floor`.

Separately, **negative principal balance and negative par are set to zero**, and this is recorded as an advisory — *"Some of Principal Balance is updated from Negetive to 0"* — so the correction is visible rather than silent.

### 4.7 Ratings

- **Moody's rating value containing `*` or `/` is cleared.** These are qualifiers, not ratings.
- **Fitch rating and Fitch country rating of `WR` are cleared** (withdrawn rating).
- **If Moody's rating value is present but the WARF value is missing, the WARF is looked up** from the rating-value mapping table.
- **For Wells Fargo only:** a Moody's rating value that is one to five asterisks is copied verbatim into `moody_rating_warf`.
- **Ratings are only taken from the source named in the deal's data-source priority.** If a rating field appears in the priority table but is not marked as PDF-sourced, the PDF value is ignored.
- **S&P recovery rating is reduced to its first digit.** `3B` becomes `3`. No digit at all means the field is blanked.

### 4.8 Recovery rates

- **A recovery percentage above 100 fails the deal**: *"Recovery rate may be >100"*.
- **S&P recovery rate above 100 fails the deal** the same way. This field can hold several rates packed as `rating|rate` pairs joined by `^` — each pair is checked individually.
- When the report splits S&P recovery rate across several rating-specific columns, they are folded into one caret-delimited value in that packed format.

### 4.9 Industry

- **Industry name and industry code are copied into their `_t` variants** on load.
- **An industry code of `0` is cleared** in both the code and `_t` fields.
- **S&P industry beginning with `Region` is cleared** — a region is not an industry.
- **For six specific deals** (500016295, 500035419, 500039282, 500046425, 815025559, 820069455) the numeric industry code is translated into a name via the industry bucket table, for both the Moody's and S&P buckets.
- Numeric suffixes in brackets are stripped from industry names.

### 4.10 Country

- **If country name is blank but region has a value, region is used as the country.**
- **Country names are translated to country codes** via the lookup table. **If a country name is on neither the name list nor the code list, the deal fails**: *"Country Name … Does Not Exist In DB"*.

### 4.11 Default status and defaulted date

- **If default status is blank, the defaulted date is cleared.** A date without a status is meaningless.
- **If default status is not `D`, the defaulted date is cleared** (applied after the Moody's file load).
- **If no asset in the deal carries default status `D`**, a confirmable warning is raised: *"DEFAULT_STATUS 'D' not present for this deal!!"* — unusual but not fatal.

### 4.12 PIK (payment in kind)

The rules differ by trustee.

- **Citibank:** if the capitalised-interest column was present in the report, `is_pikking` is set to `Y` where capitalised interest is greater than zero, and blanked where it is zero.
- **All other trustees**, where PIK was not supplied by a data file:
  - Capitalised interest greater than zero → `is_pikking = Y`
  - Capitalised interest of zero → `is_pikking` blank
  - **If the capitalised-interest column was *not* in the report, the column is then cleared entirely** after the flags are set — it was a derived working value, not reported data.
- Where a data file supplies a PIK flag, the raw value is normalised through the PDF data lookup first. **A value that survives normalisation but is still not recognised fails the deal**: *"Invalid value found in pik_flag column for IS_PIKKING after lookup normalization"*.
- For State Street deals PIK comes from the `pik_amount` field; for Citibank from `pik_amount_outstanding`.

### 4.13 Principal balance and par

- **If par balance is blank, principal balance is copied into it.** Same for `par`.
- **If principal balance in original currency is populated and the original currency equals the deal currency, the principal balance is copied into it** — no conversion needed.
- **For US Bank and La Salle|US Bank: a negative principal balance in original currency is set to zero**, recorded as an advisory.
- **If any principal balance is null, an advisory is raised**: *"Please check some principal_balance contain null values"*.

### 4.14 Spread and index adjustment

- **Western Alliance:** spread is reduced by the index adjustment wherever an index adjustment exists.
- **BNY, non-EUR deals:** spread is reduced by the index adjustment. Any resulting negative spread is then **set to zero**.
- **BNY, EUR deals:** index adjustment is cleared entirely.
- **Fixed-coupon assets:** index adjustment is cleared.
- **CRE CDO deals:** industry, S&P industry, Fitch industry, industry codes and country name are all cleared, and every identifier is consolidated into Trustee ID.

### 4.15 Underscores

A stored procedure strips underscores from issuer name and other text columns after load — the extraction engine uses underscores as internal padding.

### 4.15A First-lien last-out assets

**Where the loan lien value reads "first-lien last-out", `is_FLLO` is set to `Y` and the loan lien is cleared.** The FLLO flag and the lien position are alternatives, not companions — an FLLO asset carries the flag and no lien number.

### 4.15B Recovery rate formats

The "above 100 fails the deal" test on S&P recovery rate handles **three shapes**, and checks every rate in each:

- several `rating|rate` pairs joined by `^` — **each pair tested individually**
- a single `rating|rate` pair — the rate tested
- a bare number

### 4.15C Industry bucket translation — what actually gets written

For the six deals listed in §4.9, the bucket lookup does **not** replace the code. It writes the resulting name into **`industry_name` and `industry_name_t`**, leaving the code in place. The S&P side is separate and conditional: **`sp_industry` is only translated where its value is a whole number** — a value that is already a name is left alone.

The bracketed-number strip (`Aerospace & Defense (2010)` → `Aerospace & Defense`) applies to **industry name, S&P industry and Fitch industry**, not to industry name alone.

### 4.16 Collateral manager and participation seller

**`CM_NAME` and `LOAN_PARTICIPATION_SELLER` are cleared on every deal.** These are populated later in the pipeline, not from the trustee report.

### 4.17 Dummy identifiers

Any identifier value beginning `SCDODUMMY` is cleared from **CUSIP, reference CUSIP, ISIN, LoanX ID, loan identifier, Trustee ID and CRE underlying deal ID** — these are placeholders inserted during matching.

### 4.18 Paydown date and amortisation overlap

**If the amortisation schedule came from a data file, the report must not also supply paydown date or principal paydown.** If it does, the deal fails: *"You R taking Amort from xls as well as PDF…"*.

**Where the amortisation did *not* come from a data file:**
- If every collateral row shares the same paydown date, paydown date and principal paydown are cleared for the whole deal — a single shared date is not a real amortisation schedule.
- For any individual asset whose paydown date equals its maturity, paydown date and principal paydown are cleared — the final repayment is not an amortisation event.

## 5. Transactions

### 5.1 Transaction type normalisation

| Report says | Stored as |
|---|---|
| `Receive`, `Buy`, `Addition`, `Purchased` | **PUR** |
| `Sell`, `Deliver`, `Removal`, `Sold` | **SLD** |

- **A `Receive` or `Deliver` with no credit status is tagged `Restructuring`.**
- **Any transaction whose type is not `PUR`, `SLD`, `Extra_PUR`, `Extra_SLD` or `UNK` is deleted.**
- If unrecognised types remain after this, the deal fails: *"Plz check Trancation Type Wrong"*.

### 5.2 Sign convention

- **A sale (`SLD` or `Extra_SLD`) with a positive par has its par made negative.**
- Later, and definitively: **`SLD` par is forced negative, `PUR` par is forced positive.**
- **Total proceeds are always stored as a positive number** — a negative value is sign-flipped.

### 5.3 Unknown transaction types resolved by sign

For transactions still marked `UNK`:

- **Negative principal → `PUR`**
- **Positive principal → `SLD`**

**Exception:** a restructure whose principal came from the Prior Par column stays `UNK` and has its total proceeds cleared. This applies only where **both** conditions hold — the transaction was mapped with `PRIOR_PAR` **and** it is tagged `Restructure` by the mapping team.

### 5.4 Duplicate "extra" transactions

The report sometimes lists the same trade twice, once in the main section and once in an extras section. The extras are matched against the main list and deleted where they duplicate:

- **Where the extra has no trade date, or the matching main row has none:** delete the extra if the main list has a row with the same issuer name and par, or the same CUSIP / ISIN / loan identifier / LoanX ID and par.
- **Where both have trade dates:** delete the extra if a main row matches on issuer name and trade date, or on identifier and par, **and** the money lines up:
  - Extra total proceeds blank, main populated → delete if a main row matches on issuer, trade date and the extra's par as its total proceeds
  - Both populated → delete if a main row matches on issuer, trade date, total proceeds and par
  - Main total proceeds blank → delete if a main row matches on issuer, trade date and par

**Whatever extras survive are then relabelled** — `Extra_PUR` becomes `PUR`, `Extra_SLD` becomes `SLD`.

### 5.5 Principal, proceeds and par reconciliation

Run separately for purchases and sales, and separately again for transactions with and without a credit-status value:

- **If no transaction has a principal and any has interest**, total proceeds are moved into principal and total proceeds cleared.
- **If no transaction has a principal and none has interest**, total proceeds are copied into principal (and kept in total proceeds).
- **Consistency test:** the application computes `par × (principal ÷ par)` and compares it to principal. **If any row is off by more than 0.05**, the whole set is rebuilt — par takes the principal value with the correct sign, principal takes total proceeds, and total proceeds is cleared. Recorded as an advisory: *"PAR and TOTAL_PROCEEDS data has been updated for TRansaction Schema"*.
- **Second consistency test:** `principal + interest` should equal total proceeds. **If any row is off by more than 0.05, total proceeds is cleared** for the set. Recorded as *"Toatal_Proceeds data has been Blank for Transaction Schema"*.
- **If every row has a principal, no total proceeds and no interest, principal is copied into total proceeds.**

### 5.6 Par is never null

**A null par becomes zero.**

### 5.7 Price

- **A price below 2 is multiplied by 100** — it was reported as a decimal fraction rather than a percentage.
- **A restructure or exchange with no price is given a price of 100.**
- **A reprice (`Reprice_In` / `Reprice_Out`) with no price is given 100**, and a blank credit status is set to `Reprising`.

### 5.8 Credit status inference

The "CT value" referred to here is the stored column **`CT_Value`**, mapped from the report's `transaction_reason`. It is not written to the ASCII, but three rules read it:

- Credit status blank and `CT_Value` starts `Exchange` → **`Exchange`**
- Credit status blank and `CT_Value` starts `Restructure` → **`Restructure`**
- `CT_Value` of `Reprice_In` or `Reprice_Out` → **price set to 100 where blank, credit status set to `Reprising` where blank** (§5.7)

`CT_Value` starting `Restructure` is also what marks a transaction eligible for the Prior Par exception in §5.3.

### 5.8A Book date standing in for trade date

**Where the Principal Activity mapping supplies a book date, and every trade date *and* every settlement date in the section is blank, the book date is read as the trade date.** It is not stored as a column of its own — it simply fills the trade-date slot when nothing else did.

### 5.9 Trade date versus settlement date

Applies to **BNY deals** only, driven by the per-deal configured method:

- **Method is "trade date"** and no transaction has a trade date → settlement date is moved into trade date and settlement date cleared.
- **Method is "settle date"** and no transaction has a settlement date → trade date is moved into settlement date and trade date cleared.
- **No method configured** raises a confirmable warning: *"Method date not captured for this deal"*.

### 5.10 Citibank total proceeds

**For Citibank purchases with no credit-status value, total proceeds are cleared.**

### 5.11 Issuer name is mandatory

**A transaction with a blank or missing issuer name is rejected and the deal fails**, quoting the collateral key, transaction type, CUSIP, ISIN and par so the row can be found in the report.

### 5.12 Security ID defaults

- Null security ID becomes an empty string.
- Blank security ID type becomes `LIN`.
- A security ID starting with the deal ID gets type `DAT`.

## 6. Principal Activity / Principal Reduction

### 6.1 One source only

The report sometimes carries principal activity in more than one section, each tagged with a flag. **Only the first flag value found is kept; every row carrying a different flag is deleted.**

### 6.2 Account names must be known

**Rows whose account name appears in neither the principal account-name lookup nor the interest account-name lookup are deleted.** Unrecognised accounts are dropped rather than loaded.

Where account names need correcting, a lookup maps the reported name onto the correct one. Failures raise *"Error in updating data according to account name from principal activity excel. Please check T_Principal_Account_Name_Lookup table."*

### 6.3 Excluded transaction types

Rows are deleted where the combination of transaction type and issuer name matches the exclusion lookup.

### 6.4 Notes are not assets

**Rows whose issuer name starts with `Class` and ends with `Note` or `Notes` are deleted.** These are tranches, not collateral.

### 6.5 Total proceeds is the sum

**Total proceeds is set to interest plus principal, and interest and principal are then both cleared.** Nulls count as zero. **Run three times over the course of the upload**, so a value written back by a later step is re-summed.

### 6.6 Total proceeds must not be blank

**If any Principal Activity row has no total proceeds, the deal fails**: *"Total_Proceeds is blank for One or Multiple Issuer_Name in Principal Reduction. Please check or Contact BT Team."*

If BT has added a `Total_Proceeds` exemption for the deal, this is downgraded to a confirmable warning instead.

### 6.7 Price

**A price below 2 is multiplied by 100.**

### 6.8 Date range

**A date outside 01/01/2000–01/01/2099 fails the deal**: *"Date is less than 01/01/2000 or greater than 01/01/2099. Please chk Principal Activity Table."*

### 6.9 Transaction type must be mapped

**If transaction type is unmapped, the deal fails**: *"Please map the column transaction_type column"*.

## 7. Test Results

### 7.1 Pass and fail

- Anything starting `Pass` → **`PASS`**
- Anything starting `Fail` → **`FAIL`**
- A `result` containing `-` → **cleared**

### 7.2 N/A handling

`N/A` clears the field for: `test_current`, `initial_value`, `test_trigger`, `prior`, `max_min`, `comments`. A `-` clears `comments` and `max_min`.

**If `test_current` is N/A, the pool name and test name are also cleared** — the whole row is treated as not applicable.

### 7.3 Trustee test flag — the `is_tr_test` rule

Three cases, in order:

1. **If every row's `is_tr_test` is blank, every row is set to `N`.** The trustee report did not mark which tests are trustee tests, so none are assumed to be.
2. **If some rows have a value and others are blank, only the blanks are set to `N`.** The populated ones are trusted as they stand.
3. **If the column was never mapped at all**, an advisory is raised — *"is_tr_test not mapped in xml, do u want to continue?"* — and processing continues.

Additionally, **if the deal has 10 or fewer test rows**, blanks are set to `N` and the test-result data file is loaded to fill in the rest.

### 7.4 Implausible values

- **A test value above 10,000 in initial value, current, trigger or prior deletes that row** — but only where the test name is duplicated. A one-off large value is kept.
- **A `test_current` above 10,000 is moved into `test_balance` and `test_current` cleared**, where test balance is empty. A balance was reported in the current-value column.
- **A trigger above 200 on a test that is not a rating or factor test** moves the current value into test balance and clears current — same reasoning.

### 7.5 Empty rows

**A row is deleted when max/min, initial value, trigger, current, balance and prior are all blank *and* the result is blank or reads `N/A`.** Nothing left to report.

### 7.6 Duplicate test names

**Where the same test name appears more than once, every occurrence after the first is tagged `Duplicate`** rather than deleted, so the data is retained for review.

Two details matter when reading the result. **The tag is written into the `table_no` column, not into the test name** — the test name you see is unchanged, and the row loses the record of which report table it came from. And **name matching is case-sensitive**: `Class A OC Test` and `Class A OC test` are two different tests, not a duplicate pair.

### 7.7 As-of date

**Test rows whose as-of date does not match the trustee run date are deleted** (rows with no as-of date are kept).

### 7.8 Trigger inheritance

Where the deal has a configured source/destination test pair, **a blank trigger on the destination test is filled from the source test** — but only if the source test name appears exactly once.

### 7.9 Date to percentage *(extended, uncommitted)*

A test value that was captured as a date is converted back to a percentage. Applies to `test_current`, `test_trigger`, `test_prior` and — newly — **`prior`**.

### 7.10 Record order

`record_order` is set to the row's sequence number.

## 8. Notes and Tranches

### 8.1 Blank-out rules

**A value containing `-` or `N/A` clears the field** for: payment frequency, coupon type, current principal, payment date, interest rate, principal pay-down, interest distribution, Moody's credit rating.

### 8.2 Tranche identity

- **`trustee_tranche_id` is set to the row's sequence number**, and re-set after every step that changes the row count, so it always runs 1…n with no gaps.
- **`trustee_id` is hardcoded to `9133` on every deal.** It is not read from the report.
- **Duplicate tranche descriptions are suffixed `[1]`, `[2]`, `[3]`** so each is distinguishable — **including the first occurrence**, so a name appearing twice becomes `…[1]` and `…[2]`.

### 8.3 Tranche consolidation

Where a tranche description starts `Class `, it is truncated at **the first space at or after position 7** — `Class A-1 Senior Secured Notes` becomes `Class A-1`; a description with no space after the class letter is kept whole.

Rows are then consolidated on the shortened description, **summing current principal and interest rate**. Consolidation is not on the description alone: **every other column must match too** — payment frequency, coupon type, payment date, principal pay-down, interest distribution and Moody's credit rating. Two `Class A-1` rows with different coupon types stay as two rows.

### 8.4 Recovery rate class name

The recovery rate class name is taken from the deal's rollup configuration and applied to every tranche whose description matches the configured prefix.

### 8.5 Duplicate rows

Where tranche description and interest rate both repeat, only the first row is kept.

## 9. Account Balance

### 9.1 One row only

`account_id` is set to `1` — Account Balance holds a single row per deal per period.

### 9.2 Empty rows deleted

**If both account principal balance and account interest balance are null or empty, the row is deleted.**

### 9.3 Export date

`EXPORT_DATE` is set to the run date.

### 9.4 Payment dates in the past

**If the trustee run date is later than the next payment date, that date is cleared.** Same for the next determination date. A "next" date that has already passed is stale.

### 9.5 Trustee run date

- **Blank fails the deal**: *"Trustee rundate is blank in accountbalance table, please check."*
- **A run date already used for this deal fails the deal** — the guard against reprocessing the same reporting period. Overridden by a `Refinance deal` exemption or by ticking Compare ASCII.

### 9.5A Trustee numerators

**Trailing letters are stripped from `oc_trustee_numerator` and `ic_trustee_numerator`.** Trustees frequently append the currency to the figure — `1,234,567 USD` — and the letters would otherwise fail the numeric conversion.

### 9.6 Deal and manager names

- **Blank trustee deal name fails the deal.**
- **A trustee deal name that differs from last period raises an advisory** — informational only, so a genuine rename does not block the run.
- **A collateral manager name that differs from last period raises an advisory** likewise.

## 10. Misc Account and Miscellaneous

### 10.1 Filling the two balance columns

- **If every row is missing `account_balance_orig`, the global balance is copied into it** — but only when the count of rows missing the original balance equals the count missing `account_name_partial`, which is how the application confirms the column genuinely wasn't reported rather than being partly blank.
- **The reverse also applies**: if every row is missing the global balance, the original balance is copied into it.

### 10.2 Account type derived from the name

Where account type is blank, it is derived from the account name, **first match winning**:

| Account name contains | Account type |
|---|---|
| "Ramp-Up" and "Interest" (in either order, with or without the hyphen) | **Reserve** |
| "Principal" | **Principal** |
| "Reserve" | **Reserve** |
| "Interest" | **Interest** |
| anything else | **Other** |

The Ramp-Up rule is checked first specifically so that a "Ramp-Up Interest Account" is classified as a reserve rather than as interest.

### 10.3 Account type must be valid

**Any account type other than `Principal`, `Reserve`, `Interest` or `Other` fails the deal**: *"Wrong value in MiscAccount Table in Account Type column"*.

### 10.4 Account type carried forward from last period

Where an account name appears **exactly once this month and exactly once last month**, last month's account type is reused. Where it appears **the same number of times in both months**, the types are matched across in order. Otherwise the type is left as derived — the application will not guess when the counts disagree.

A per-deal lookup can also force account types by account name.

### 10.5 Account name format

**A Misc Account `account_name_partial` must contain a `/`.** Without it the deal fails.

### 10.6 Duplicate misc names

- **Duplicates are found by grouping on misc type *and* misc name** — the same name under two different types is not a duplicate. **Every row in a repeating group is suffixed `[1]`, `[2]`, `[3]`, including the first**, so two identical names become `…[1]` and `…[2]` — you never see a bare name sitting beside a suffixed one. For three specific deals — 824880062, 824346087, 824488835 — this is the documented behaviour.
- **Separately, duplicate misc names raise an advisory**: *"Duplicate names exist in Miscellaneous tab."*

### 10.7 Mandatory columns

**Missing `MISC_TYPE`, `MISC_NAME` or `ACCOUNT_NAME` fails the deal**, naming the column.

### 10.8 Row-count comparison with last period

**If the number of Misc Account rows differs from last month, a mismatch is recorded**: *"MisAcount data mismatched with previous month"*. Same check for Miscellaneous.

## 11. Amortization

### 11.1 What the schedule is split by

Each deal is configured to split its amortisation by issuer name or by a specific identifier. The configured value is stored per month so the choice is auditable, defaulting to **issuer name** where nothing is set.

### 11.2 Zero and negative paydowns

- **Rows with a negative principal paydown are deleted**, and the count is added to the deal's deleted-amort counter.
- A separate routine removes zero-value amortisation rows.
- Every deletion increments the counter, so the number of rows dropped is visible.

### 11.3 Duplicate paydown dates

Where the same issuer has the same paydown date more than once, the duplicates are deleted and counted.

### 11.3A Identifiers on amortisation rows — validated, not reclassified

**This is the one place in the application where a malformed identifier is discarded rather than moved to Trustee ID.** Each identifier is format-checked on the way in:

- **CUSIP** must be exactly 9 characters, alphanumeric, underscore-free, containing a digit. **Anything else is stored blank.**
- **ISIN** must be 12 characters, alphanumeric, underscore-free, containing a digit **and** pass the check digit — retried once with `O` replaced by zero. **Anything that still fails is stored blank.**
- **LoanX ID** must be 8 characters starting `LX`, alphanumeric, containing a digit. **Anything else is stored blank.**

**Trustee ID is the exception — it is promoted, not discarded**, and only into an empty target: an 8-character `LX…` value moves to LoanX ID, a 9-character value moves to CUSIP, a 12-character value passing the check digit moves to ISIN. **A Trustee ID longer than 50 characters is stored blank.**

### 11.3B Issue ID *(Deutsche Bank)*

**`issue_id` is captured from its own mapped column**, added for the Deutsche Bank amortisation requirement — the change this branch exists for. Dollar signs are stripped from the value along with the standard CSV quote and separator unescaping.

Note also that the Amortization table spells its loan identifier column **`loan_identifirer`** — two letters transposed. A search for the correct spelling finds nothing.

### 11.4 Junk characters

`S.? r.l.` is corrected to `S.a.r.l.` in issuer names — a recurring mis-read of the French company suffix.

### 11.5 Data-volume check

**If this month's amortisation has fewer than half as many rows as last month's**, it is flagged in the Data Missing log: *"This Month Amortization Table has 50% less data than previous month"*.

### 11.6 Source recorded

The source of the amortisation data (report or data file) is stored on the deal master.

- **A blank rating is stored as the literal text `blank`** rather than left null, so the row is not mistaken for missing data.
- **If this month has no stratification data at all, last month's rating agency / rating type / rating rows are copied forward** with blank values, marked as sourced from `ICRA`.
- **A stratification table containing a blank row fails the deal.**
- A stratification section that fails to parse triggers an **OCR re-read of the PDF** and one retry.

## 12A. Recovery Rate and Retention

Two schemas that are part of the run but have almost no rules of their own. They are listed here so their absence elsewhere reads as a finding rather than an omission.

**Recovery Rate** holds three columns — the collateral key, `recovery_rate_class_name` and `recovery_rate_value`.

- **The class name comes from the deal's rollup configuration**, the same source that fills it on Notes (§8.4).
- **Its distinct count is compared against the tranche class names, and a disagreement is written to the Data Missing log.**
- `recovery_rate_value` has no rule of its own — cleaned by the general rules, compared against last month, written as reported.

**Retention** holds five columns — minimum retention percentage and amount, current retention percentage and amount, and the result. **None of them carries a business rule.** All four numeric columns are on the decimal register, the result is uppercased on output, and the schema takes part in the previous-month comparison. That is the whole of it.

## 12B. Dummy Asset — processing a deal with no collateral *(uncommitted)*

Ticking **Process Without Collateral Data** injects a single synthetic collateral row so a deal that reports no assets can still be run through.

Exactly three columns are set: **issuer name `Dummy Asset`**, **principal balance `0.00`**, and **currency code taken from the dropdown beside the checkbox**, which is populated from the currency list in `T_DataValidation_LookUp`. Every other collateral column is left blank, and the whole schema then flows through the ordinary rules on that one zero-balance row.

Ticking the box also **suspends the guard that rejects a report carrying more than one collateral table.**

## 13. Issuer names

### 13.1 Text cleaning

Applied to every issuer and tranche name from every source:

- HTML entities decoded — `&amp;` → `&`, `&quot;` → `"`, `&nbsp;` → space, `&lt;` → `<`, `&gt;` → `>`, `&apos;` → `'`
- Line breaks removed
- Apostrophes escaped for storage; `'s` handled specifically
- Leading and trailing commas and spaces trimmed

### 13.2 Junk character detection

Issuer names in Collateral, Transactions and Principal Activity are tested against a configurable pattern. **Any name that matches the junk pattern fails the deal**, naming the table and the value:

> *"Please remove junk character from issuer_name or modify the regex on 'System ⇒ LookUp Table Data ⇒ T_Junk_IssuerName_LookUp' table."*

Names on the junk-issuer allow-list are exempted — these are legitimate names that happen to contain unusual characters. **The allow-list is now read across all deals rather than for the current deal and run date only** *(uncommitted)*, so an exemption added for one deal now applies everywhere.

### 13.3 Duplicate issuers

Issuer names appearing more than once in collateral are identified and logged, because they affect how the amortisation schedule is calculated.

### 13.4 Unfunded Commitment *(now an error, uncommitted)*

**Any rolled-up issuer name cell equal to `Unfunded Commitment` raises a hard error** naming the column. Previously this only went to the run log.

## 16. Order of execution

Order matters — a value set by an early rule can be overwritten by a later one.

1. **Extraction and value cleaning** (§1) — as each value is read
2. **Identifier space removal** (§1.11) — before anything else touches the dataset
3. **Day/month format standardisation** (§1.2)
4. **Rollup** (§1A) — report lines reassembled into collateral rows; amounts apportioned; unplaceable values pushed into new rows
5. **Dummy Asset injection** (§12B) — where Process Without Collateral Data is ticked
6. **Equity balance backfill from secondary sections** (§4.4)
7. **Load into the processing tables** — PDF deals from the report; Excel-priority deals from the Moody's file with the report filling gaps
8. **Blank-cell fill** (§1.10A) — a second reading fills cells still empty after load
9. **Post-load logic** — duplicate transaction cleanup, identifier separation, currency splitting, country codes, industry names, recovery-rate ceilings, tranche descriptions, account balance, notes
10. **Principal Activity capture** — including notes and test results
11. **Post-principal logic** — negative balances to zero, misc balances, misc account types, price and trade-date handling, amortisation cleanup
12. **Moody's data file 1**, then **2**, then **3 and 4** — each matched by the identifier chain in §1B, each overwriting where the data-source priority allows
13. **Final post-data-file rule set** (the largest) — junk issuer names, WARF, maturity, industry codes, currency, IDX, defaulted dates, par, Bloomberg tickers, PIK, Trustee ID promotion, deal-specific overrides, transaction reconciliation, misc account types, previous-month comparison
14. **ASCII generation** — coverage tests, critical checks, and the output formatting in §16B

## 16A. Row keys — how the sheets join

Two columns are created by the application rather than reported, and everything else depends on them.

- **`display_seq`** is a collateral row's position in the list, assigned on load. Every per-row rule in this document — clearing an equity coupon, setting a rating, fixing an issuer name — is addressed by `deal + month + year + display_seq`.
- **`display_seq_coll`** is the link back to collateral from Transactions, Principal Activity, Amortization and Recovery Rate. It is the collateral row that transaction or paydown belongs to.

**Both are written to the ASCII zero-padded to four characters** — row 7 appears as `0007` — and `display_seq_coll` is output under the heading **`Collateral_Key`**. A row whose collateral key matches no collateral row is orphaned.

## 16B. Output formatting

Applied as the ASCII is written, after every rule in this document. These change how a value **looks in the output file**, not what is stored — which matters when a value in the database does not match the value in the file.

| Treatment | Applied to |
|---|---|

| **Title-cased** | Payment frequency, coupon type, coupon calendar method, Misc Account account type |
| **Accent and odd-character stripped** | Issuer name, industry name, country name, S&P industry, S&P seniority, service name, industry name (T), coupon calendar method |
| **Zero-padded to 4 characters** | `display_seq`, `display_seq_coll` |
| **Four decimal places** | Spread |
| **`MM/DD/YYYY`** | Every date column, plus `user_variable_1` on Collateral and Notes |

## 17. Previous-month comparison

For each of the eleven schemas, this month is compared with last month. Last month is read from the live tables, falling back to the history tables if the live tables have nothing.

Three findings are recorded, all as advisories:

- **"\<Table\> has data in this month but in previous month there was no data"**
- **"\<Table\> has no data in this month but in previous month there was data"**
- **Per column: "In Table \<x\> \<column\> has data in this month but in previous month there was no data"** — and the reverse

The point is to catch a column that silently stopped being captured because the report layout changed.

## 18. Critical checks written to the Data Missing log

Recorded during ASCII generation. These are review flags, not failures.

- **Spread, adjusted spread, index cap, index floor and current interest rate**: a count of values above 25
- **Amortisation**: more than 50% smaller than last month
- **Any collateral column entirely empty**, or populated in fewer than half the rows (default status is exempt from the half-populated check)
- **Equity assets with no industry name**
- **Non-equity assets with blank spread, current interest rate, adjusted spread or index floor**
- **Defaulted assets with any of those five fields blank**
- **Any column whose name contains "price", in any schema, with a value above 150** — and separately **a value of zero or missing**. This is not just MTM: it covers `mtm_price`, `mv_bid_price`, `mv_purchase_price`, `mv_market_value_price`, `purchase_price` and `discount_price` on Collateral, and `price` on Transactions and Principal Activity. The check reads the database column list at run time, so a price column added later is picked up without a code change
- **Recovery rate class name and tranche class name disagree**
- Field counts per schema, for coverage reporting

## 20. Screens opened from this one

Everything above describes what the application does to your data on its own. This section covers the screens the Bulk Upload page opens, what each is for, and what it writes back — because several of them change the outcome of the run.

### 20.1 The four message types

Every rule in this document that "fails the deal", "raises an advisory" or "records a mismatch" is really writing a row into one error table with a **message type**. The Validation screen is where those rows surface, in four separate grids:

| Type | Name | What it means | Where it appears in this document |
|---|---|---|---|
| **PS** | Process Stop | **The deal fails.** Processing halts for that deal. | Every "the deal fails" rule |
| **YN** | Yes / No | **A confirmable warning** — the operator decides whether to continue. | Every "confirmable warning" rule, e.g. *"DEFAULT_STATUS 'D' not present for this deal!!"* |
| **DM** | Data Mismatch | **Recorded for review**, not blocking. Clicking the row opens a drill-down. | §1.8 "recorded for review", §10.8 row-count mismatches |
| **MSG** | Log message | **An advisory**, written to the run log. Informational only. | Every "recorded as an advisory" rule |

Understanding the difference matters: a **PS** row is why a deal stopped, a **YN** row is a decision someone made, and a **MSG** row changed nothing.

### 20.2 The Validation screen

Opened by clicking a deal's error cell in the main grid. It shows the four grids above for that deal and run date, and works out the previous month so the comparison drill-downs have something to compare against.

It ends in one of two buttons, and the choice is the operator's:

- **Proceed** — the run continues despite the warnings.
- **Stop** — the run halts.

Three **DM** rows are clickable and open a drill-down:

- **"Data mismatch"** opens the **column-value review grid** — the values from §1.8 that were recorded rather than failed. What the operator accepts here is written back into the checked-columns set, so **this screen decides whether those values are kept**.
- **"MisAcount"** and **"Miscellaneous"** each open a **side-by-side previous-month comparison**: this month's rows and last month's rows for that schema, with a comparison column per field. Last month is read from the live table, taking the most recent period earlier than this one. These back the row-count mismatch rules in §10.8.

### 20.3 The mapping-problem screen

Opened by clicking one of two cells in the main grid:

- **"Mapping Matched" showing *Column Name Mismatch*** — the data file's column headings no longer match the stored mapping.
- **"Data_File" showing *Excel mapping not present*** — no mapping exists for a file the deal needs.

It lists the affected files, and double-clicking one opens the right mapping screen for that file type. **The two entry points route differently**, which is why the same file name can open different screens:

| File | From *Column Name Mismatch* | From *Excel mapping not present* |
|---|---|---|
| Moodys DF1 | Collateral Moody's mapping *(re-check mode, file path passed in)* | Collateral Moody's mapping *(fresh mapping)* |
| Moodys DF2 | Second data file mapping | — |
| Moodys DF3 | Multiple data file mapping | — |
| Tranche | Notes / Test Result mapping, opened for `Note` | — |
| TestResult | Notes / Test Result mapping, opened for `Test_Result` | — |
| Amort | — | Amortisation mapping |
| Transaction | — | Principal Activity mapping |

**Two of these write to the deal record on success.** Completing the amortisation mapping sets **`SourceOfAmort` to `Excel`** on the deal master and **`IsAmortExcelLoaded` to `Y`** for the period — which is exactly the flag §4.18 tests when it refuses to accept a paydown date from both the report and a data file. Cancelling leaves the source as `pdf`.

### 20.4 The mapping-change screen

Opened **during processing**, but only when the operator has ticked one of the four mapping-change options on the main form — Major or Minor, Partial or Full. If none is ticked, the deal is simply stamped `Mapping_Issue = 'NC'` (no change) and the screen never appears.

The screen asks what changed. On save it writes:

- **`Mapping_Issue`** = the change type chosen on the main form.
- **`Remarks`** = the existing remark plus each `change type - what changed` pair the operator entered.
- Any wording not seen before is added to the comment history so it is offered next time, and a newly typed change type is added to the change-type list.

> **A defect worth knowing about.** The closing quote on the Remarks update is only appended when the assembled text passes a length threshold. **When the remark is short, the statement is malformed and the update fails**, reporting *"Problem in Data Update of Reamarks"*. The mapping issue and remarks are then not saved, even though the operator filled the screen in.

### 20.5 The column-value review screen

Opened from the Validation screen's "Data mismatch" row. It lists every **distinct** table / column / value triple that failed the permitted-value check in §1.8 — the ones recorded rather than failed — with a tick box against each.

Three buttons, and they do different things:

- **Save** — **permanently whitelists every ticked value.** This is the important one: the value is written to a lookup so it never flags again, on this deal or any other.
  - For **`issuer_name`**, the value goes into that schema's issuer allow-list, `T_<schema>_Issuer_Lookup` — with one special case: the transactions staging table maps to **`T_Transaction_Issuer_Lookup`**, not to a name built from the table name.
  - For **every other column**, the value goes into **`T_Column_Value_Validation_Master`** as a table / column / value row.
  - The screen stays open after saving, and reports *"Data saved successfully"* or *"Some data not updated properely in db"*.
  - **Ticking nothing and pressing Save is rejected**: *"Please choose atleast one value to add"*.
- **Proceed** — asks *"Do you want to continue?"*; on Yes the run carries on **without** whitelisting anything. The values stay flagged for next month.
- **Stop** — abandons.

The distinction matters operationally: **Proceed accepts the value for this run only; Save accepts it for ever.**

### 20.6 The data-file mapping screens

Four screens share one design. Each maps **a column of a processing schema to a column of the data file**, and each row of the mapping carries a **priority**.

| Screen | Maps | Mapping table |
|---|---|---|
| Collateral Moody's mapping | Collateral ← Moody's data file 1 | `T_Collateral_Moodys_Mapping` |
| Second data file mapping | Collateral ← Moody's data file 2 | `T_Collateral_Moodys_Second_Mapping` |
| Multiple data file mapping | Collateral ← Moody's data files 3 and 4 | `T_Collateral_Moodys_Multiple_Mapping` |
| Notes / Test Result mapping | Notes or Test Results ← their data file | `T_Notes_Excel_Mapping` |

**Priority is what §4.7 and §1B refer to.** More than one data-file column can map to the same schema column; the priority decides which one wins, and which source is allowed to overwrite the report.

What they all do:

- **Read the data file's headings** and store them, so the mapping dropdowns offer real column names rather than free text.
- **Reject a mapping to a column that does not exist** in the schema: *"'\<name\>' in not a valid column name.."*.
- **Reject duplicate mappings** — *"Duplicate mapping exist."* on the collateral screens, and on the Notes / Test Result screen *"Excel mapping has duplicate records in 'Excel_File_Column'"*.
- **Refuse to save with nothing mapped**: *"No column mapping exist..."*.
- **Refuse to save before a file has been chosen**: *"Please Browse For The Required Moodys Excel"*.

**The audit trail is the part worth knowing about.** When a data-file column that was previously mapped is no longer present in this month's file and the operator points the mapping at a different column, the change is not silent:

- The remap is written to a **`…_Columns_Modified`** table — deal, the column that was not found, the column it was mapped to instead, month, year and priority.
- Any previous entry is first archived to the matching **`…_ModifiedHist`** table together with **who made the change, their Windows user name, the machine name and the timestamp**.

So "the trustee renamed a column and someone repointed the mapping" is always recoverable, per deal and per month.

**Exception handling.** Each collateral screen has a second tab writing to a parallel `…_Mapping_exception_handling` table, for mappings that deviate from the standard. Two rules apply there:

- **Remarks are mandatory** — *"Remarks cannot be empty in Exception Handling tab."*
- A blank schema column raises a confirmable warning: *"Some of the Collateral_Moodys_Column is empty in Exception Handling tab. Do you want to continue"*.

The Notes / Test Result screen additionally offers **Upload Blank Template**, which loads an empty mapping template for a deal that has none.

### 20.7 The amortisation mapping screen

Maps eleven amortisation fields to data-file columns: issuer name, ISIN, CUSIP, Trustee ID, paydown date, paydown value, loan identifier, reference CUSIP, LoanX ID, special issuer, and **Issue ID** — the Deutsche Bank field from §11.3B.

It also carries the **split-by dropdown** — the setting behind §11.1. The options are Issuer Name (the default), CUSIP, Reference CUSIP, ISIN, LoanX ID, Loan Identifier and Trustee ID.

**The screen enforces the pairing.** If the split is set to an identifier, **that identifier's column must also be mapped**, or the screen refuses to close: *"Kindly Map \<identifier\> Column Index"*. You cannot ask the schedule to be split by CUSIP without telling the application where the CUSIP is.

On OK it writes the choice to **`T_Amort_Splited_By`** for that deal, month and year — inserting on first use, updating thereafter — so the split used in any given month stays auditable. It also validates that every mapped column actually exists in the file: *"Columns '\<name\>' does not exist in the excel. Please correct the mapping."*

As noted in §20.3, completing this screen is what sets `SourceOfAmort` to `Excel` and `IsAmortExcelLoaded` to `Y`.

### 20.8 The Principal Activity mapping screen

Maps 23 fields to data-file columns — and this is where several columns documented earlier as "mapping-driven only" are actually set: **`transaction_reason` (which becomes `CT_Value`), `book_date`, `account_name`, `interest_rec`, `fees` and `purchaser_affiliation`**, alongside the identifiers, dates, par, currency, price, principal, interest and total proceeds.

**There are two mapping modes**, and which one is used decides how the file is read:

- **By column position** — the mapping stores the Excel column letter, in `T_PrincipalActivity_Data_Mapping`.
- **By column heading** — the mapping stores the heading text, in `T_PRINCIPAL_ACTIVITY_DATA_MAPPING_With_Header`.

A file whose columns move between months is safe under the second mode and breaks under the first. A separate lookup, `T_PrincipalActivityXLS_Column_Lookup`, translates a database column name to its expected spreadsheet heading.

The screen refuses to save before a file is chosen — *"Please Browse For The Required PricipalAcivity Excel"* — and rejects a mapping that does not line up with the file: *"Please Map with the excel correctly."*

### 20.9 The bulk processing screen

Reached from its own button on the main form rather than from Browse. It selects deals over a date range and processes them together, writing back per deal: **`IsRollUpLoaded='Y'`** once the rollup is loaded, **`Status='PROCESSED'`** on completion, and the operator's validation note into `T_Deal_Process_Bulkupload`. It also offers export to Excel and a bulk update across the selected rows. **Selecting no date range is rejected**: *"Please select datetime range"*.

### 20.10 Reachability

Two things are worth recording so nobody hunts for them:

- **The `Amort_Browse`, `moodys_browse` and `PR_Browse` methods on this form have no callers.** They open the amortisation, Moody's and Principal Activity mapping screens directly, but nothing invokes them. The mapping screens are reached only through the mapping-problem screen described in §20.3.
- **`clsOutputAscii.cs` and the TAT calculation screen are not reachable from this page**, despite being modified in the current working tree. They belong to Output Autoprocess and Manual Excel Upload.
- **The Upload Deals screen is constructed as a field on this form but never shown from it.** It is a separate screen in its own right; nothing on this page opens it.
